# B2 RocketMQ 事务消息 + 本地消息表：讲解笔记

## 0. 要解决的问题（一个例子）

B1 的下单最后一步是本地事务 B：写 `orders` + `order_item` + `trade_snapshot` + `order_status_log`。
B2 要在这之后再发一条"订单已创建"（`OrderCreated`）事件到 MQ。最直接的写法：

```java
orderPersistService.saveNewOrder(...);   // ① 提交数据库事务
producer.send(orderCreatedMsg);          // ② 发 MQ
```

两步之间任何一处断掉都会出错：

| 出事的位置 | 结果 |
|---|---|
| ① 成功，② 前进程被 kill / MQ 超时 | **订单建了，消息没发**：下游永远不知道这个订单 |
| 把 ② 挪到 ① 前面，② 成功后 ① 回滚 | **消息发了，订单没建**：下游处理了一个不存在的订单 |
| 把 ② 放进 `@Transactional` 方法里面 | 和上一行一样：消息已经发出去收不回来，事务却还可能回滚；而且等网络期间一直占着数据库连接 |

数据库和 MQ 是两个系统，没有一个"同时提交两边"的按钮。本任务就是用两种行业通行做法把这两步绑在一起。

## 1. 和原项目的差异

- **千言 IM 用的是 Kafka 普通消息**：业务写完库后直接 `send`，发失败就记日志，丢了就丢了——聊天消息另有离线拉取兜底，可以接受。
- **交易链路不能丢**，所以这里新学两种"本地事务 + 消息"一致的做法：
  - **RocketMQ 事务消息**：先发一条消费者看不到的**半消息**，再执行本地事务，事务成功才**提交**让消费者可见，失败就**回滚**删掉；如果生产者在提交前挂了，Broker 会主动**回查**生产者"这个事务到底成没成"。一致性由 MQ 协助完成。
  - **本地消息表**（Outbox）：把"要发的消息"当成一行数据，和订单**写在同一个本地事务里**，靠数据库事务保证"有订单就一定有待发消息"；再由定时任务扫描未发送的记录去发 MQ。一致性完全靠自己的数据库，不依赖 MQ 有没有事务能力。
- 两种方案下游都可能**收到重复消息**（回查、重发都会造成重复），所以消费端必须按消息 ID 幂等——这一点和 IM 里"消息去重"思路一致，但这里是强制要求。

## 2. 为什么订单建好后"发事件、下游自己处理"，而不是 order 同步调用下游

**一句话**：下单只该对"订单建没建成"负责；通知商家、推送、写搜索索引、统计这些都是"订单建成之后的事"，用事件解耦后，下游慢了、挂了、新增了，都不影响下单成功与否，也不用改 order 的代码。

拿本项目的真实下游举例（后续任务会陆续出现）：

| 下游 | 做什么 | 若 order 同步调用它 |
|---|---|---|
| realtime（Netty 推送） | 给商家后台推"你有新订单" | 推送服务重启 3 秒，期间所有下单都失败 |
| ES 订单索引 | 让商家能搜到订单 | ES 慢 2 秒，下单接口就慢 2 秒 |
| 对账 / 统计 / AI 运营助手 | 记录交易数据 | 每加一个下游，order 都要多一次 Feign、多一个超时配置、多一种失败分支 |

同步调用的三个问题：
1. **可用性相乘**：order 的成功率 = 自己 × 每个下游。下游越多越差
2. **耗时相加**：买家要等所有下游都处理完才看到"下单成功"
3. **耦合**：order 必须知道有哪些下游；下游失败了，订单已经提交，order 还得自己想办法重试——等于把消息队列的活又写了一遍

发事件的代价：下游是**最终一致**（晚几百毫秒才知道），而且要处理重复消息。对"通知、索引、统计"这类场景完全可以接受。

**什么时候仍然要同步调用**：调用结果决定这次下单能不能成功的——比如 B1 的**库存预占**。占不到库存就必须当场告诉买家失败，所以 B1 用 Feign 同步调用，不发事件。判断标准："下游的结果会不会改变本次请求的返回"。

## 3. 设计评审（你的方案 → 补充）

### Q1 两种方案怎么共存 —— 你：配置开关二选一 ✅

对的。如果两种同时开，同一个订单会发出两条事件，下游虽然能靠幂等挡住，但这是给自己找麻烦。
本项目用一个配置项 `merchanthub.order.event-mode`：`TX_MESSAGE`（事务消息）或 `OUTBOX`（本地消息表），默认用 `OUTBOX`（理由见第 9 节"两种方案取舍"）。
真实项目里一般只选一种，这里两种都做是为了学习和对比。

### Q2 回查靠什么判断 —— 你：消息带订单号，回查时查订单表 ✅，补一个时序上的坑

方向完全正确：回查时手里只有那条半消息，所以消息里必须带"能查到本地事务结果的业务键"，也就是 `order_no`。本项目把它放进消息的 `keys` 字段，消息体里也带一份。

**坑**：要是回查来得太早，本地事务还没跑完呢？

```
t=0s   发半消息成功，开始执行本地事务（写订单）
t=?    Broker 回查：查 orders，没有这个 order_no → 返回 ROLLBACK → 半消息被删
t=?+1  本地事务提交了 → 订单存在，消息却没了  ❌
```

这里"查不到订单"有两种可能：一是本地事务已经回滚了，二是本地事务还没跑完。光查订单表区分不出来。
本项目的做法是让"回查一定发生在本地事务结束之后"：
- 本地事务设超时 `@Transactional(timeout = 5)`：超过 5 秒必然回滚
- 半消息设"免回查时间" `CHECK_IMMUNITY_TIME_IN_SECONDS = 30`：Broker 至少等 30 秒才会第一次回查

等到回查真正发生时，本地事务一定已经有了结果。这时查得到订单就 `COMMIT`，查不到就 `ROLLBACK`。
（还有一种做法：查不到订单时先返回 `UNKNOW` 让 Broker 稍后再来查，等消息存在超过阈值才判 `ROLLBACK`。两种做法本质一样，都是靠时间窗口来区分。）

### Q3 本地消息表的字段 —— 你：消息状态、发不出去要报错、发给下游、内容是订单和消息 —— 方向对，需要细化

| 你说的 | 落到字段 | 补充 |
|---|---|---|
| 消息状态 | `status`：0 待发送 / 1 已发送 / 2 发送失败（不再重试） | 扫描任务只扫 `status = 0` 的记录 |
| 发不出去要报错 | `retry_count`、`next_retry_at`、`last_error` | 行业做法不是"一失败就报错"，而是**有限次重试 + 退避**：第 1 次失败过 10 秒再试，第 2 次过 20 秒、40 秒……超过上限（比如 10 次）改成 `status = 2`，打 ERROR 日志并告警，转人工处理。MQ 抖几秒属于正常现象，没必要每次都告警 |
| 发给下游 | `topic`、`tag` | 消息表只记"发到哪个 Topic"，**不记具体发给谁**：谁订阅了谁就收到，这正是第 2 节说的解耦 |
| 内容是订单和消息 | `event_id`（唯一）、`biz_key`（= order_no）、`payload`（JSON） | 消息体放**事件**，不放整张订单：`eventId、orderNo、tenantId、buyerId、payAmount、createdAt`。下游需要明细时再按订单号来查。放整单的话，订单表结构一改，所有下游都要跟着改 |

另外加一个索引 `(status, next_retry_at)`，扫描任务用的就是这个条件。

### Q4 消费端幂等 —— 你：用 msgId，存 MySQL —— MySQL ✅，msgId ❌ 要换成自己的 ID

**为什么不能用 RocketMQ 的 msgId**：msgId 是**每调用一次 send** 由客户端生成一个。来看本地消息表的重发：

```
第 1 次 send：Broker 其实收到了（msgId=A），但响应超时 → 我们以为没发成功
第 2 次 send（补偿重发）：又生成一个新的 msgId=B
消费者收到 A 和 B → 按 msgId 去重：A≠B，处理了两次 ❌
```

所以去重键必须是**我们自己生成、重发也不变的 ID**：本地消息表里的 `event_id`（雪花 ID）。它在写订单的同时生成，以后不管重发多少次都是同一个值。
事务消息方案也一样，`event_id` 放在消息体和 `keys` 里。这是行业通行做法："业务唯一键去重，不依赖中间件的消息 ID"。

**存 MySQL ✅，关键是"去重记录"和"业务处理"放在同一个本地事务里**：

```
BEGIN
  INSERT INTO consumed_event (consumer_group, event_id) ...   -- 唯一键冲突 → 说明处理过 → 直接返回成功
  执行业务处理
COMMIT
```

为什么不用 Redis 的 `SETNX`：Redis 和 MySQL 不在同一个事务里。先 SETNX 成功、业务却失败了 → 重投过来时被当成"已处理"跳过，消息就丢了；先做业务、再 SETNX 之前挂了 → 重复处理。
用 MySQL 时两步要么一起提交、要么一起回滚。

### 技术选型（我定的，不考）

客户端直接用 `rocketmq-client` 5.3.1（和 Broker、TestSupport 同版本），自己写配置 Bean。
没用 `rocketmq-spring-boot-starter`：它和 Boot 3.5 的适配要另外核对，而且对事务监听器封装得比较深，不利于看清"半消息 → 执行本地事务 → 回查"这三步。
没用 Spring Cloud Stream：事务消息在 Stream 里要绕好几层配置。

## 4. 方案一：事务消息（已实现）

### 4.1 代码在哪

| 文件 | 作用 |
|---|---|
| `service/OrderPlacer` | 下单最后一步的接口。`OrderCreateService` 只调用它，不关心底层是哪种方案 |
| `mq/tx/TxMessageOrderPlacer` | 发半消息 → 拿到本地事务结果 → 失败时把原始异常抛给上层 |
| `mq/tx/OrderTxListener` | `executeLocalTransaction` 负责写订单；`checkLocalTransaction` 负责回查 |
| `mq/tx/TxMessageConfig` | `TransactionMQProducer`：生产者组、回查线程池、发送超时 |
| `mq/OrderEventCodec` | 事件和消息之间的转换：`keys = "订单号 事件ID"`，用户属性 `EVENT_ID` |

### 4.2 本项目特有的几处处理

1. **RocketMQ 客户端会吞掉本地事务里的异常**：`executeLocalTransaction` 抛出的异常不会传给调用方，客户端只记一行日志，然后按 UNKNOW 处理。所以监听器自己 catch 住异常，放进 `LocalTx`，再由 placer 原样抛出。这样下单接口能报出真实原因，比如数据库故障。
2. **半消息发不出去（MQ 不可用）时，订单就不建**：这是事务消息方案的代价，MQ 一挂就不能下单。下面的方案二没有这个问题，第 6 节会做对比。
3. **回查有两道防线**（Q2 的落地）：
   - 第一道是免回查时间 30 秒，并且大于本地事务超时 5 秒
   - 第二道在回查端：**订单查不到、并且消息出生还不满 30 秒，就返回 UNKNOW，不判 ROLLBACK**
   - 为什么需要第二道：写测试时实测发现，回查比 Broker 配置的下限**早了约 1 秒**（见 pitfalls P17）。Broker 用它自己的时钟和生产者写入的 `bornTimestamp` 比较，两边时钟有偏差，时间窗口就会跟着偏。第二道防线只用生产者这一侧的时钟，不受 Broker 影响
   - 查库报错时返回 UNKNOW，不返回 ROLLBACK：数据库出错不代表订单不存在
4. **回查会找同一生产者组里任意一个在线实例**：测试里，回查被同一个 JVM 里另一个测试上下文的生产者接走了（P17）。这件事反过来说明：**组里的每个实例都要能正确回答任何一条半消息**，所以回查只能查共享的数据库，不能依赖本机内存。kill 实验里"重启后的新进程能接住回查"，靠的也是这一点。
5. **同一条半消息可能被回查多次，COMMIT 之后都可能再来一次**：测试日志里，订单 COMMIT 之后，Broker 又对它回查了 3 次（`checkTimes=3,4,5`）。所以回查逻辑必须可以重复执行，消费端也必须幂等。

### 4.3 自动化的破坏性场景

| 测试 | 场景 | 结论 |
|---|---|---|
| `OrderTxMessageIT.localTxFailed_noOrder_andMessageNeverVisible` | 半消息已发出，写订单时数据库报错 | 订单不存在，消费者等 8 秒也收不到这条消息 |
| `OrderTxCheckIT.commitLost_checkFindsOrder_commits` | 本地事务已提交，但 COMMIT 没送到 Broker（kill 实验的自动化版） | 回查发现订单存在 → COMMIT → 消费者收到 |
| `OrderTxCheckIT.checkFindsNoOrder_rollsBack_neverVisible` | 回查时订单不存在 | 先回答几次 UNKNOW（消息还年轻），等消息够老了再 ROLLBACK，消费者收不到 |
| `OrderTxListenerTest` | 查库失败、消息体损坏、消息还年轻 | 分别返回 UNKNOW、ROLLBACK、UNKNOW |

## 5. 🧑 kill 实验记录（2026-11-20）

**步骤**：`deploy/b2/start-order.sh 120000`（本地事务提交后停顿 120 秒）→ `place-order.sh` 下单 → 看到"本地事务已提交"后执行 `kill -9` → 立刻用 `start-order.sh` 重启 → 等待回查日志 → 用 `show-msg.sh <订单号>` 查看消息。

**看到的现象，对照两阶段 + 回查流程**：

| 阶段 | 现象 | 说明 |
|---|---|---|
| ① 发半消息 | `RMQ_SYS_TRANS_HALF_TOPIC` 能查到，`ORDER_EVENT` 查不到；属性 `TRAN_MSG=true`、`REAL_TOPIC=ORDER_EVENT`、`PGROUP=order-tx-producer` | 半消息存在系统 Topic 里，消费者看不到。真实的目标 Topic 记在属性里 |
| ② 本地事务提交 | `mh_order.orders` 里已有这个订单 | |
| kill -9 | COMMIT 没有发出去 | 这时"订单在、消息不可见"，是不一致窗口 |
| ④ 回查 | 重启后约 30–60 秒，日志打出 `事务回查 orderNo=... checkTimes=5 订单存在=true → COMMIT_MESSAGE` | Broker 找到了同组的新实例来问；新实例查共享数据库，确认订单存在 |
| ③' 提交 | `ORDER_EVENT` 里能查到了，属性多了 `TRANSACTION_CHECK_TIMES=5`、`TRAN_PREPARED_QUEUE_OFFSET` | 提交 = Broker 把消息从半消息 Topic 复制到真实 Topic |

**补充说明**：
- 提交之后，半消息 Topic 里**仍然能查到**原消息。这是正常的：RocketMQ 的存储只追加、不删除，"这条半消息已处理"另外记在 `RMQ_SYS_TRANS_OP_HALF_TOPIC` 里
- `checkTimes=5`：重启之前的那几轮回查，因为组里没有在线实例而失败，但次数照样累加

**两次失败的尝试，本身也是结论**：
1. 第一次沟通花了太久，kill 了 6 分钟才准备重启。半消息回查满 15 次（10 秒 × 15）后被丢进 `TRANS_CHECK_MAX_TIME_TOPIC`，**订单存在，但事件永远不会投递**。说明事务消息的回查有时间上限，过了上限就保证不了一致性，仍需对账兜底
2. 第二次立刻重启了，还是没等到回查：重启的实例在下第一单之前，没有给 Broker 发心跳（P18）。修复后的第三次成功，自动化测试是 `OrderTxRestartIT`

## 6. 引入 Flyway（我定的，不考）

**结论**：B2 起，order 服务改用 Flyway 管理表结构；product-inventory 暂时不动，等它第一次需要改表（预计 B3）时再切换。

**理由**：
- B1 用的是 `spring.sql.init` + `CREATE TABLE IF NOT EXISTS`，只能"没有就建"。**已有的表加字段、加索引它做不了**，脚本改了，旧库也不会跟着变
- B2 是第一次在已经有数据的库上加表；B3 很可能要改 `inventory_reservation` / `orders` 的字段。越晚引入，基线越难整理
- Flyway 给每次变更编一个版本号（`V2__xxx.sql`），执行记录写在 `flyway_schema_history` 表里。每个环境执行到哪个版本一目了然，测试库和本机库走的是同一套脚本

**本项目做的调整**：
- 原来的 `db/schema.sql` 原样搬成 `db/migration/V1__init.sql`，作为基线，**以后不再修改**（改表写新的 V 文件）
- `baseline-on-migrate: true` + `baseline-version: 1`：你本机的 `mh_order` 库是 B1 时建的，没有 Flyway 历史表。Flyway 会把它记成"已经在 V1"，只执行 V2 及以后的脚本。已在本机验证过：日志依次打出 `Successfully baselined schema with version: 1` 和 `Migrating schema mh_order to version "2 - order outbox"`
- 依赖要同时加 `flyway-core` 和 `flyway-mysql`：Flyway 10 起把 MySQL 支持拆成了单独的包，只加 core 启动时会报 `Unsupported Database: MySQL`

**代价**：多一个依赖；已经执行过的 V 文件不能再改，改了 Flyway 启动时校验和不一致会报错。这本身也是一种约束，防止有人偷偷改历史脚本。

## 7. 方案二：本地消息表（实现）

### 7.1 代码在哪

| 文件 | 作用 |
|---|---|
| `db/migration/V2__order_outbox.sql` | 表 `order_outbox`，字段按 Q3 的讨论结果 |
| `mq/outbox/OutboxOrderPlacer` | **一个本地事务**里写订单和消息记录；事务提交后触发一次快路径投递 |
| `mq/outbox/OutboxRelay` | 投递和补偿：`publishAsync`（快路径）和 `scan`（定时兜底）都走 `publish` |
| `mapper/OrderOutboxMapper` | `selectDue` 查出到期的待发送记录 / `claim` 抢占 / `markSent` 标记已发送 / `markRetry` 记一次失败 |
| `mq/outbox/OutboxConfig` | 普通生产者（不需要事务消息）、快路径线程池、`@EnableScheduling` |

### 7.2 本项目特有的设计

1. **"提交后立即发一次" + "定时扫描兜底"**：只靠扫描的话，每条消息平均要晚半个扫描周期才发出去。行业里普遍的做法是：提交后马上异步发一次，正常情况下几十毫秒就送达；扫描只负责处理失败的。
2. **一定要在 `afterCommit` 里发，不能在事务里发**：在事务里发出去，事务后面还可能回滚，就变成"消息发了订单没建"。
3. **快路径的线程池满了就直接丢弃任务**：记录已经在表里，扫描会补发。不用 CallerRuns 策略，因为那会让下单请求的线程自己去发 MQ，MQ 一慢下单就跟着慢。
4. **多实例扫描靠条件更新"抢占"**：两个 order 实例可能同时扫到同一条记录，只有 `UPDATE ... WHERE id = ? AND status = 0 AND ...` 返回 1 的那个才去发。思路和 B1 的库存条件更新一样。
5. **失败重试用指数退避**：10s → 20s → 40s……最长 10 分钟。失败满 10 次标记为 `status = 2`，打 ERROR 日志（生产环境接告警）。人工排查后把 status 改回 0，记录就会重新进入投递。
6. **没上 XXL-Job**：定时扫描暂时用 Spring `@Scheduled`。多实例同时扫描靠第 4 点的抢占保证不重复发。XXL-Job 留到 B3 超时关单时再引入，到时这个扫描任务也会迁过去。

### 7.3 🔍 审代码：藏的 bug 与修复

**bug**：`OrderOutboxMapper.claim` 抢占时执行了 `SET status = 1`。

| 步骤 | 这一行的状态 |
|---|---|
| ① claim：`SET status = 1` | 还没发，status 就已经是"已发送" |
| ② send 抛异常（MQ 不可用） | |
| ③ markRetry `WHERE ... AND status = 0` | 一行都匹配不上（日志 `updated=0`），失败没被记下来 |
| ④ 扫描 `WHERE status = 0` | 永远扫不到 → **消息丢失**，并且表里看起来"已发送"，没有任何报错，也没有告警 |

**你的结论**：找到了 `status = 1`，后果说对了："订单建了，消息没发出去，系统以为已经发了，不会再补"。

**根因**：把"我正在发"和"已经发成功"合成了同一个状态。
**修复**：claim 只把 `next_retry_at` 推后作为租约，**不改 status**；`markSent` 才改成 1，并且带上 `status = 0` 条件。租约到期还没有结果（比如发送途中进程被 kill），记录自动重新变成"到期"，被下一轮扫描接手。
**验证**：`OrderOutboxCompensationIT` 的 3 个用例在 bug 版本上全部失败，修复后全部通过。

### 7.4 破坏性实验 ②：真实停掉 Broker（我做的，2026-11-20）

`docker stop mh-broker` → 下单 → 等一会儿 → `docker start mh-broker`：

```
16:16:03 下单成功（Broker 已停，接口照样秒回）         ← 相对事务消息方案的最大差别
16:16:03 快路径失败 第 1 次，5s 后重试   error=Send [3] times, still failed
16:16:12 扫描失败   第 2 次，10s 后重试
16:16:22 扫描失败   第 3 次，20s 后重试
16:16:42 扫描失败   第 4 次，40s 后重试
16:16:52 docker start mh-broker
16:17:22 扫描：投递成功                status=1 retry_count=4
```

- 退避间隔 5 → 10 → 20 → 40 秒（实验时把 base 调成了 5 秒）
- Broker 恢复后**最多要等一个退避间隔**消息才送达（这次等了 30 秒）。代价是故障期间的消息恢复得不够快；好处是长时间故障时不会每秒刷一次 MQ
- 自动化版本是 `OrderOutboxCompensationIT`（用 spy 模拟发送异常，没有真停共享容器，原因写在测试注释里）

### 7.5 写测试时又踩到的"多实例"现象

补偿测试第一次跑的时候，"MQ 不可用"对重试不生效：同一个 JVM 里缓存着的其他测试上下文（`SchemaIT` 等，默认也是 OUTBOX 模式）也在扫描同一个测试库，把记录抢过去用自己没被 spy 的生产者发掉了。这和 P17 是同一类问题。放到生产环境里，这就是"别的实例接手补发"，属于正常行为。解决办法：测试配置默认关闭扫描（`src/test/resources/application.properties`），只有补偿测试打开。

## 8. 消费端幂等（实现）

- `mq/consumer/MerchantNoticeService.handle`：**同一个本地事务**里先插 `consumed_event`（唯一键 `(consumer_group, event_id)`），再写 `merchant_order_notice`。唯一键冲突说明处理过了，直接返回 `false`，消息也算消费成功
- **先插、靠唯一键判断**，而不是"先 SELECT 查一下有没有，再插"：两条重复消息同时到达时，两边 SELECT 都查不到，就都会处理
- 业务失败时返回 `RECONSUME_LATER`，RocketMQ 稍后重投（第一次重投默认延迟 10 秒）。去重记录已经随事务回滚，所以重投时能正常处理
- 消息体坏了（解析失败）：记 ERROR 日志，然后确认掉，不让它无限重投
- 消费者只订阅 Tag `ORDER_CREATED`，而且不关心消息是用哪种方案发出来的，两种方案的消息格式一致

**自动化的破坏性场景**（`MerchantNoticeConsumerIT`）：

| 用例 | 场景 | 结论 |
|---|---|---|
| `sameEventDeliveredThreeTimes_...` | 同一个事件投递 3 次，3 个 msgId 各不相同 | 处理方法被调用 3 次，只写了 1 条通知。按 msgId 去重的话会写 3 条 |
| `businessFails_dedupRolledBack_...` | 把通知表改名，模拟下游表故障 → 恢复 | 失败那次没有留下去重记录，重投后正常写入 1 条。用 Redis SETNX 先占位的话，这条通知就永远丢了 |
| `placeOrder_noticeWritten` | 端到端：本地消息表方案下单 | 消费者写出 1 条通知 |

**实测发现的重复来源**：`OrderTxRestartIT` 的事务消息，在 `ORDER_EVENT` 里被这个消费者收到了 3 次（1 次处理，2 次跳过）。推测和 4.2 第 5 点一样：COMMIT 之后 Broker 又回查了几次，每次都提交了一份。重复消息不只是理论上可能有，测试里真的出现了。

## 9. 两种方案取舍 + 为什么不用 Seata

| 对比项 | 事务消息（方案一） | 本地消息表（方案二） |
|---|---|---|
| MQ 挂了还能不能下单 | **不能**：半消息发不出去，订单就不建（4.2 第 2 点） | **能**：只写数据库，MQ 恢复后补发（7.4 实验：Broker 停着，下单照样秒回） |
| 一致性靠谁 | MQ 和生产者配合（半消息 + 回查） | 只靠自己的 MySQL 本地事务 |
| 最坏情况 | 回查有**时间上限**（周期 × 15 次）。生产者组整体宕机超过这个时间，半消息被丢弃，订单在、事件永远不发（第 5 节第一次 kill 实验） | 重试满上限后标记失败、发告警，**记录一直在表里**，人工把状态改回 0 就能重发 |
| 对 MQ 的要求 | 必须支持事务消息（RocketMQ 有，Kafka 的事务语义不一样） | 任何 MQ 都行 |
| 额外成本 | 要写回查接口；回查只能依赖共享数据库 | 多一张表、多一次 insert、一个扫描任务 |
| 踩过的坑 | 回查找"同组任意实例"、时钟偏差、重启后没心跳（P17 / P18） | 抢占时改状态导致消息丢失（🔍 那个 bug） |

**本项目默认用本地消息表**：下单是核心链路，"MQ 挂了也能下单"更重要；而且它最坏的情况可以人工兜底，事务消息过了回查上限就没救了。事务消息适合"不想多一张表、MQ 本身很稳定"的场景，两种在行业里都很常见。

**为什么不用 Seata**（答出一条即可）：
1. **用不着强一致**：下游是通知、索引、统计，晚几百毫秒没关系。用 2PC 把下游也拉进同一个全局事务，等于把第 2 节说的"下游挂了不影响下单"又丢掉了
2. **性能**：Seata AT 模式要加全局锁。库存、订单这种热点行，每次都要和 TC（事务协调器）通信、等全局提交，并发一高就成了瓶颈
3. **多一个中间件**：要部署 TC 服务，它本身还要做高可用。本地消息表只用现有的 MySQL 和 MQ
4. 项目约定不引入（CLAUDE.md），行业里交易链路也更常用"本地事务 + 可靠消息 + 对账"

**以后会学的（预告，不考）**：B3 会用 RocketMQ 延迟消息做超时关单，还会做对账任务，找出"有订单、没事件"和"有预占、没订单"的记录，作为两种方案都需要的最后一道兜底。
