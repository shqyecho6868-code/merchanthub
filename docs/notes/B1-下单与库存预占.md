# B1 下单 + 库存预占：讲解笔记

## 1. 和原项目的差异

千言 IM 没有交易链路，金额、库存、订单状态、交易快照在本项目里全部是新写的，没有旧代码可以改。
原项目只有雪花 ID 工具能借用，但它在多实例下 workerId 会冲突（pitfalls P1），要先修好，再拿来生成订单号。

## 2. 事务边界（已定：按 D2 保持两个服务）

```
order 服务                                   product-inventory 服务
──────────                                   ─────────────────────
1. 校验参数、生成 order_no
2. Feign: 查 SKU（价格/规格/状态） ───────────▶  只读查询
3. Feign: 预占库存(order_no, 多个 SKU) ────────▶ 【本地事务 A】
                                                 按 sku_id 排序
                                                 逐个条件更新 inventory
                                                 写 inventory_reservation
                                                 任一失败 → 整个事务回滚
4.【本地事务 B】
   写 orders(待支付) + order_item + trade_snapshot + order_status_log
```

- **全占或全不占**靠事务 A 保证：多个 SKU 的条件更新和预占记录都在 inventory 侧同一个本地事务里，任何一个 SKU 库存不够就抛异常、整体回滚
- **订单数据完整**靠事务 B 保证
- **已知缺口（B1 不处理）**：事务 A 提交了、事务 B 失败了（或 Feign 超时，order 侧不知道到底占没占上），库存会被"悬空占用"。B2/B3 用预占记录表按 `order_no` 找到这些占用，判断订单不存在后释放。所以预占记录表从 B1 开始就要写，B1 先不读它
- 为什么不用 Seata：CLAUDE.md 明确不引入；行业里交易链路更常见的做法是"本地事务 + 可补偿的记录 + 对账/超时兜底"，也就是这里的方案

## 3. 雪花 workerId：从中间件"领号"

### 你的方案
启动时通过一个中间件中转，让各实例错开 workerId。**方向是对的**，这正是行业做法：美团 Leaf-snowflake 用 ZooKeeper，很多团队用 Redis 或 DB 表。

### 本项目的具体做法（Redis 租约）
- hutool 的 `Snowflake(workerId, dataCenterId)` 各 5 位，合起来 10 位 = 1024 个槽位
- 启动时从槽位 0 开始依次尝试 `SET mh:snowflake:slot:{n} {实例ID} NX EX 90`，第一个成功的就是自己的号
  - `NX` 保证同一个槽位只会被一个实例拿到
  - `EX 90` 是租约：实例宕机后不续期，90 秒后号自动回收，不会越用越少
- 后台每 30 秒续期一次，续期前要先确认 value 还是自己的实例 ID（compare-and-expire），防止把别人的号续上
- 槽位换算：`dataCenterId = slot / 32`，`workerId = slot % 32`
- 用全局命名空间（所有服务共享 1024 个槽位），这样 order_no 和 pay_no 也不会撞号

### 为什么选 Redis、不选别的
| 方案 | 不选的原因 |
|---|---|
| 配置文件里给每个实例手写 workerId | 扩容时要人工分配，容易配重，这就是旧代码的问题 |
| ZooKeeper 顺序节点（Leaf） | 本项目没有 ZK，不为这个引入新组件 |
| MySQL 表领号 | 可以做，但过期回收要自己写定时任务，Redis 的 TTL 天然就有 |
| Nacos 实例序号 | Nacos 不提供稳定的实例序号 |

### 代价和边界情况
- **启动依赖 Redis**：Redis 不可用时服务直接启动失败。这是有意的，宁可起不来，也不能带着可能重复的号运行
- **租约丢了**（Redis 抖动、长时间 GC 导致没续上，号被别人拿走）：续期时发现 value 不是自己，就记 ERROR 日志并停止发号（之后调用 `nextId` 直接抛异常），不能继续用旧号
- **时钟回拨**：hutool 检测到回拨会抛异常，不发号。这里不额外处理，记录为已知限制

## 4. 库存预占记录表 inventory_reservation

### 4.1 唯一约束：(order_no, sku_id)
用一个例子：订单 9001 买了 2 件白色 L（sku 101）+ 1 件黑色 M（sku 102），表里会有两行：

| order_no | sku_id | quantity | status |
|---|---|---|---|
| 9001 | 101 | 2 | RESERVED |
| 9001 | 102 | 1 | RESERVED |

- **只对 `order_no` 唯一**：第二行插不进去，一个订单只能占一个 SKU，多 SKU 订单直接没法存。所以你问的"只在 order 上会不会重复"，答案是反过来：不是会重复，而是**合法的多行也被拦住了**
- **只对 `sku_id` 唯一**：一个 SKU 一辈子只能被一个订单占，显然不对
- **`(order_no, sku_id)` 唯一**：含义是"同一个订单对同一个 SKU 最多占一次"。重试、重复请求再来一次，插入就会撞唯一键，这正是我们要防的"重复预占"

### 4.2 状态：三个，不是两个
| 编码 | 状态 | 什么时候变成这样 |
|---|---|---|
| 10 | RESERVED 已预占 | 下单（B1） |
| 20 | CONFIRMED 已确认扣减 | 支付成功（B2/B3） |
| 30 | RELEASED 已释放 | 买家取消 / 支付超时（B3） |

你漏的是 **RELEASED**。为什么一定要有它：超时关单的消息可能被**重复投递**（MQ 至少一次投递，后面任务会讲）。如果没有状态，第二条消息来了还会再执行一次 `available + 2`，库存凭空多出 2 件。
有了状态，释放写成 `UPDATE inventory_reservation SET status=30 WHERE order_no=? AND sku_id=? AND status=10`，影响 1 行才去加回库存；影响 0 行说明已经释放过（或已经确认扣减过），直接跳过。这和订单状态机的 CAS 是同一招。
CONFIRMED 和 RELEASED 都是终态，互斥：支付成功和超时释放同时到达时，只有一个 CAS 能成功。（B1 只会写 RESERVED，后两个状态 B2/B3 用到时再讲细节）

### 4.3 重试撞唯一键：应该返回**成功**（幂等）
还是用订单 9001 举例，时间线：

```
order 服务                          inventory 服务
  │── 预占(9001, 101×2, 102×1) ──▶  事务提交成功：库存已扣，记录已写
  │        ✗ 响应在网络上丢了 / 超过了 Feign 超时
  │  （order 只知道“超时”，不知道到底成没成）
  │── 重试 预占(9001, 同样内容) ───▶  插入记录 → 撞唯一键
```

- **如果返回失败**：order 认为"库存不足"，告诉买家下单失败。但实际上库存已经被 9001 占着，买家没订单、库存却少了 3 件，只能等补偿任务来释放。重试本来就是为了解决"不知道"，结果被这个失败答复弄错了
- **返回成功**：第二次请求想要的结果是"9001 占住了这些库存"，而这件事**已经成立**，所以如实回答"成功"。这就是幂等：同一个请求执行 N 次 = 执行 1 次（A3 笔记里 Stripe 那篇文章讲的就是这个）
- **但要核对内容**：撞唯一键时要比对已有记录的 sku 和数量是否和这次请求一致。一致 → 返回成功；不一致（同一个订单号却要占不同的东西）→ 说明调用方有 bug，返回错误。不能看到订单号一样就盲目说成功

### 4.4 唯一键为什么能"兜住"并发的重复请求
两个一模一样的请求**同时**到达，都先查了一下"有没有记录"，都看到没有，都往下走：
- 两个事务都去扣库存、都插记录，后插的那个撞唯一键 → 抛异常 → **它所在的整个事务回滚，包括它扣的库存**
- 所以库存只被扣了一次。关键前提是：**扣库存和插记录在同一个本地事务里**。如果分开提交，扣库存那步已经生效了，回滚不掉
- 行业里常见的写法是**先插记录、再扣库存**：插入相当于"幂等闸门"，重复请求在第一步就被拦下，不会去抢 inventory 行锁

## 5. 下单请求设计（评审你的答案）

### 5.1 请求里带什么
你的答案：数量、商品 ID；价格用后台的；购买时间、金额由后台算。**大方向对**，补三点：

| 字段 | 谁给 | 说明 |
|---|---|---|
| `items[].skuId` | 客户端 | 是 **SKU ID**，不是商品 ID：价格和规格挂在 SKU 上，"白 L"和"黑 M"可能价格不同 |
| `items[].quantity` | 客户端 | |
| `expectedPayAmount` | 客户端（可选） | 买家在确认页看到的应付金额，**只用来比对，不用来计价** |
| buyerId | 网关从 token 解析后放进 `X-User-Id` 请求头 | **不能放在请求体里**，否则谁都能冒充别人下单 |
| 单价、金额、下单时间、tenant_id | 服务端 | 单价查 SKU，时间取服务器时间，tenant_id 取自 SKU |

**"后台价格和前端价格应该不会不一样吧？"——会不一样**，有两种情况：
1. **价格变了**：买家 10:00 打开确认页，看到 99 元；10:01 商家改价成 129 元；10:02 买家点提交
2. **恶意篡改**：有人抓包把价格改成 0.01

服务端一律用数据库里的价格计价，第 2 种就防住了。第 1 种如果直接按 129 元下单，买家会觉得被坑了，所以客户端把 `expectedPayAmount=9900` 一起传过来。服务端算出来是 12900，两边对不上，就返回"价格已变动，请确认后重新下单"。这是电商下单接口的通行做法。

### 5.2 order_no 在预占之前生成 ✅
理由就是你说的唯一键 `(order_no, sku_id)`：order 调 inventory 超时后重试时，**必须带着同一个 order_no**，inventory 才能通过唯一键认出"这是同一次预占"，从而幂等返回成功。如果到建订单时才生成，预占记录就没有订单号可记，B3 也没法按订单号找到它来释放。

### 5.3 防重复提交（B1 不做，记为遗留）
order_no 在服务端生成，只能解决"同一次请求的重试"。买家**连点两次**提交，是两次独立请求，会拿到两个 order_no、生成两个订单。行业做法是：进入确认页时，服务端先发一个下单 token，提交时带上，服务端按 token 去重（A3 笔记里讲过）。

## 6. 下单链路的代码结构（B1 第 4 步）

```
OrderController  POST /orders（X-User-Id）
 └ OrderCreateService.createOrder           ← 不加 @Transactional
    1. 合并重复 SKU、校验
    2. Feign 查 SKU 快照       → product-inventory /internal/skus/query
    3. 校验：存在、在售、已上架、同一商家；计算金额，和 expectedPayAmount 比对
    4. 生成 order_no（雪花）
    5. Feign 预占库存           → product-inventory /internal/inventory/reserve【事务 A】
    6. OrderPersistService.saveNewOrder      ← @Transactional【事务 B】
       快照 → 明细 → 订单 → 状态流水
```

本项目特有的两处调整：
- **远程调用放在事务外面**：`createOrder` 不加事务，只有第 6 步的 `saveNewOrder` 加。如果整个方法都加 `@Transactional`，在等 Feign 响应的这几百毫秒里，数据库连接会一直被占着，高并发时连接池很快就会耗尽。而且这里根本没有能回滚远程调用的事务，加了也是假安全
- **事务方法单独放一个 Bean**：Spring 的事务靠代理实现，同一个类里的方法互相调用会绕过代理，`@Transactional` 不生效（自调用失效）。所以把它拆到 `OrderPersistService`
- **Feign 超时**：连接超时 1 秒，读超时 3 秒，不重试。超时后 order 不知道库存到底占没占上，B1 先直接返回"库存服务繁忙"；可能悬空的那份预占留给 B2/B3 按预占记录补偿。因为预占是幂等的，以后也可以安全地加上重试
- **租户隔离**：预占 SQL 多加了一个 `AND tenant_id = ?` 条件。如果有人用 A 商家的 tenant_id 去占 B 商家的 SKU，条件不成立，一行都更新不到

### 7.1 为什么要按 sku_id 排序（防死锁）
订单 A 买 [101, 102]，订单 B 买 [102, 101]，同时执行，不排序会这样：

| 时刻 | 事务 A | 事务 B |
|---|---|---|
| t1 | 更新 101 → 拿到 101 的行锁 | 更新 102 → 拿到 102 的行锁 |
| t2 | 更新 102 → 等 B 释放 102 | 更新 101 → 等 A 释放 101 |
| t3 | 互相等待 → **死锁**。InnoDB 检测到后会回滚其中一个（报错 1213），用户看到下单失败 | |

排序以后，两个事务都先锁 101：B 在 101 上排队等 A 提交，等 A 结束后再执行，形不成环。**所有事务按同一个顺序加锁**，是防死锁的通用做法。

### 7.2 全占或全不占：靠"抛异常 → 整个事务回滚"
订单买 101×2、102×5，但 102 只剩 3 件：
1. 插 101 的记录，更新 101：available −2 ✅（还没提交）
2. 插 102 的记录，更新 102：`available >= 5` 不成立，影响 **0 行**
3. 你抛出 `BusinessException(INVENTORY_INSUFFICIENT)` → 事务回滚 → 第 1 步的 −2 和那条记录**一起撤销**

关键点：**影响 0 行时 MySQL 不会报错**，只是返回 0。你必须自己检查返回值并抛异常，否则 101 的预占会被提交，变成"只占了一部分"。

### 7.3 为什么用 TransactionTemplate，而不是在 reserve 上加 @Transactional
第 5 个 TODO 要捕获唯一键冲突，然后**去查已有的记录**来判断是不是重复请求。这一步必须在**本次事务已经回滚之后**做，看到的才是干净的状态。
- 如果在 `reserve` 上加 `@Transactional`，并且在方法里面 catch，那 catch 的位置还在事务里面，事务还没回滚
- 如果拆成两个方法，只给内层方法加 `@Transactional`，又会遇到 6 节讲过的**自调用失效**
- `transactionTemplate.executeWithoutResult(...)` 把事务边界写成一段代码块：块里抛异常就回滚，块外面的 catch 就是在"回滚之后"执行。这就是编程式事务的适用场景

### 7.4 先插记录、再扣库存
笔记 4.4 讲过：插入是"幂等闸门"，重复请求在第一步撞上唯一键就停下了，不会去抢 inventory 的行锁。

## 8. Code review 练习：`rows < 0` 埋的 bug

例子：订单 9001 买 101×2、102×5，102 只剩 3 件。

| | 插记录 | 条件更新 | 结果 |
|---|---|---|---|
| 101 | 101×2 | rows=1 | available −2，reserved +2 |
| 102 | 102×5 | `3 >= 5` 不成立，**rows=0，不改任何数据** | available 仍为 3，reserved 仍为 0 |

- `rows < 0` 永远不成立（影响行数只可能是 0 或 1），所以不抛异常 → 事务**提交** → order 收到**成功**
- 结果：部分预占（只占了 101），并且 102×5 这条记录是假的。付款后要发 5 件 102，实际只有 3 件 → 超卖
- B3 按记录释放：释放 SQL 如果没有防护，102 的 available 会变成 8（凭空多出 5 件）；如果有 `reserved >= n` 防护，释放失败，记录和库存对不上
- 要点：① UPDATE 条件不成立**不报错**，只返回 0；② 失败必须由代码**主动抛异常**，事务才会回滚；③ "记录"和"库存"必须同生共死

## 9. 破坏性实验：去掉 `available >= ?`

| | 有条件 | 去掉条件 |
|---|---|---|
| 成功 / 库存不足 | 10 / 90 | **100 / 0** |
| available / reserved | 0 / 10 | **−90** / 100 |
| 预占记录 | 10 条 | 100 条 |

去掉条件后，available **恰好**是 −90，说明 100 次扣减一次都没丢：行锁仍然在让它们一个一个执行。

## 10. 过关知识点串讲

### 10.1 防超卖靠哪句 SQL
```sql
UPDATE inventory SET available = available - ?, reserved = reserved + ?
WHERE sku_id = ? AND tenant_id = ? AND available >= ?
```
"判断够不够"和"扣减"写在**同一条语句**里，原子完成。条件不成立时影响 0 行，代码据此判断为库存不足。
反面例子：先 `SELECT available` 读到 1，在 Java 里判断 `1 >= 1`，再 `UPDATE SET available = 0`。两个请求可能同时读到 1、都判断通过、都写 0：卖出 2 件，库存却只减了 1。**既超卖，又丢失更新**。

### 10.2 多 SKU 全占或全不占靠什么
靠 inventory 侧 `reserve()` 里 **`transactionTemplate.executeWithoutResult(...)` 包住的那个本地事务**：
- 所有 SKU 的"插记录 + 条件更新"都在这一个事务里
- 任何一个 SKU 影响 0 行 → 代码**主动抛** `BusinessException` → 事务回滚 → 前面已经扣的 SKU 和已经插的记录一起撤销
- 两个前提缺一不可：① 都在**同一个**事务里；② 失败时**一定抛异常**（`rows < 0` 那个 bug 就是破坏了 ②）

### 10.3 行锁在这里起什么作用
InnoDB 执行 UPDATE 时，先对命中的那一行（走 `uk_sku` 索引定位到的 sku_id 这一行）加**排他锁**，并且**一直持有到事务结束**。
1. **串行化同一行的并发扣减**：100 个请求在 101 这一行上排队，每个请求读到的都是前一个提交后的最新 available，所以 `available >= 1` 的判断是准的。实验里 available 恰好是 −90，说明即使去掉条件，行锁也保证了**不丢失更新**
2. **只锁一行，不锁整张表**：买 101 的请求不会挡住买 102 的请求。前提是 WHERE 能走索引定位到行，如果 sku_id 上没有索引，就会锁住扫描到的很多行
3. **代价**：锁会持有到事务结束，这就是为什么事务要短（远程调用放在事务外、先插记录再扣库存、多 SKU 排序防死锁）

一句话：**行锁让判断准确、扣减不丢；WHERE 条件让扣到 0 就停；事务让多个 SKU 同生共死。**
