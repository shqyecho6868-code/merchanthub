# 面试自问自答

> 记录答不上来或答得不稳的问题，以及最终答案。

## A1｜迁移地图与服务划分

### Q：payment 收到支付成功后，能直接改订单状态吗？（A1 答偏）
**我当时的回答**：不能直接改，要对账。
**最终答案**：不能。每个服务只改自己的数据。主路径是 payment 发出“支付成功”事件（RocketMQ），order 消费后自己执行 `UPDATE ... SET status=已支付 WHERE status=待支付` 做 CAS，并写状态流水。对账只是兜底，用来发现消息丢失或长时间不一致。
**延伸**：order 下单时把商品价格拷贝成交易快照，之后不再回查 product；库存通过调用 inventory 预占，order 不直接改库存。

### Q：“支付成功”和“超时取消”同时发生怎么办？（A1 机制没讲清）
**最终答案**：两条路径都执行 `WHERE status = 待支付` 的条件更新，数据库行锁保证只有一个成功，另一个影响 0 行。如果超时取消先赢，这笔支付成功就成了“孤儿支付”，标记为异常交给对账处理（本项目不做退款，只记录异常）。这个机制的雏形在旧代码 `FriendRequestExpirationExecutor`：带 `WHERE status IN (未读, 已读)`，只更新未到终态的记录。

### Q：网关注入 `X-Tenant-Id` 头时，为什么必须先删掉客户端自带的同名头？
**最终答案**：下游不再验 token，网关传来的头就是**唯一的身份来源**。如果网关只是追加，请求里会同时出现客户端伪造的值和网关写入的值，下游 `getHeader()` 通常取第一个，也就是伪造的那个 → 商家 A 的员工可以读取商家 B 的数据（越权）。所以网关要先删再写，并且下游服务不能被绕过网关直接访问。

### Q：实时推送用“路由表定向推送”，路由表存哪？实例宕机怎么办？（A1 答错）
**我当时的回答**：存在 user-tenant 里。
**最终答案**：路由表是高频读写的临时状态，存 **Redis**，由 realtime 维护：连接时写入 `userId → 实例`，心跳时续期，断开时删除，并设置 TTL。实例宕机后，路由在 TTL 到期后自动失效；在此之前推送会失败。兜底思路是：推送只是“通知”，用户重连后主动拉一次订单状态，真实数据以订单查询为准。
**另一种方案**：RocketMQ 广播消费，每个实例都收到消息，本机有连接就推，没有就丢弃。简单，但实例越多浪费越大。

### Q：order 与 payment 为什么分开？（A1 稳，补充要点）
意图不同（交易意图 vs 资金动作）；外部边界不同（payment 处理回调、验签、对账）；**1:N 关系**（一个订单可以有多次支付尝试）。代价是多一条跨服务链路，以及一段最终一致性窗口。

## A3｜业务建模

### Q：超时关单和支付回调同时到达，各想把订单改成什么？靠什么只让一个成功？（A3 提示后答对）
**我当时的回答**：一个改成取消、一个改成已完成；靠超时任务的设置保证。
**最终答案**：超时关单想改成“已关闭”，支付回调想改成“已支付”（已完成要由确认收货触发）。两边都执行 `UPDATE orders SET status=? WHERE order_no=? AND status=待支付`，数据库行锁保证只有一个成功，后执行的那个影响行数为 0，代码据此停止后续操作（不再扣库存、改支付单）。超时任务只决定“什么时候去关单”，管不了并发。
**追问**：如果写成“先 SELECT 判断、再 UPDATE”，两边都读到待支付、都更新成功，最终状态取决于谁最后写；库存既被释放又被确认扣减，同一件货可能再卖给别人（超卖）。

### Q：交易快照为什么分两层，不全塞进订单明细？（A3 提示后答对）
**我当时的回答**：全塞进明细一次只能买一种商品（答偏，那是订单与明细分开的理由）。
**最终答案**：明细只冗余列表页要用的小字段（商品名、规格、单价），读起来快；完整描述、图片这类大 JSON 放 trade_snapshot，只在点“查看快照”时读，避免明细表变胖。快照防的不只是“商品被删”，也防“商品被改”（改价后买家看到的价格和实付对不上，纠纷没有证据）。

### Q：已关闭为什么必须是终态？（A3 稳，补充链路）
超时关单时库存已经释放，货可能被别人买走；如果支付回调再把订单改成已支付，同一件货卖给了两个人。所以关单后到账的钱走对账补偿，不能靠“复活”订单解决。
